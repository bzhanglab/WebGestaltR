## Submission summary

This is a major release (0.4.6 -> 1.0.0). Core computations (ORA, GSEA, NTA) are now implemented
in Rust for improved performance, and the package gains multi-omics support
(`WebGestaltRMultiOmics()`).

Two user-visible behaviour changes are documented prominently in `NEWS.md`:

* The default annotation dataset is now WebGestalt 2024. Earlier releases sent no data version to
  the server and therefore received the 2019 dataset, so identical code will return results based
  on newer annotations.
* Redundancy reduction is now opt-in, with k-medoid as the default method rather than affinity
  propagation plus weighted set cover.

No exported functions were removed and no existing argument defaults were changed, so code written
for 0.4.x continues to run.

## Note on the 'compiled code' WARNING

The Debian pre-test reports:

```
File 'WebGestaltR/libs/WebGestaltR.so':
  Found '_exit', 'abort', 'exit', possibly from ... (C)
    Object: 'rust/target/release/libWebGestaltR.a'
```

I believe this is the known false positive that arises for any package linking the Rust standard
library, and I would be grateful if you could confirm.

**The package calls none of these.** There is no call to `exit`, `_exit`, or `abort`, and no call to
Rust's `std::process::exit`, anywhere in the package or in its `webgestalt_lib` dependency. (The
only `std::process::exit` in the upstream Rust project is in a standalone command-line binary that
is not part of this R package.) The symbols enter through Rust's standard library: `std::process::abort`,
`std::process::exit` and `ExitCode::exit_process` are linked in as part of the panic runtime, and
they in turn reference the libc entry points.

**They cannot terminate R.** The build uses the default `panic = "unwind"` strategy, and every entry
point generated by `#[extendr]` is wrapped in `std::panic::catch_unwind` (`extendr-api`), so a Rust
panic is converted into an ordinary R error rather than aborting the process.

**They cannot be removed.** I reproduced the warning on Debian and tried to eliminate the symbols by
linking with `-Wl,--gc-sections`, both alone and together with `-C link-dead-code=off`. The library
shrank from 7.7 MB to 7.2 MB but all three symbols remained, because the panic runtime is reachable
and the linker cannot prove that code dead. Removing it would require `#![no_std]` or a nightly-only
`-Z build-std`, neither of which is possible for this package.

**Precedent.** Several Rust-based packages currently on CRAN carry the same finding, reported there
as a NOTE — for example `gifski` 1.32.0-2, `h3o` 0.3.0 and `prqlr` 0.10.1, each of which is `OK` on
the other flavors. The check output on those pages also carries the explanatory sentence: *"The
detected symbols are linked into the code but might come from libraries and not actually be
called."* That is exactly the situation here.

If you would prefer a different approach, I am very happy to make changes.

## System requirements

The package requires Rust (`cargo`, `rustc` >= 1.63) to build from source. Cargo dependencies are
vendored in `src/rust/vendor.tar.xz` and the build runs with `--offline` and a package-local
`CARGO_HOME` unless `NOT_CRAN=true`, so no network access or writes outside the package directory
occur during installation.

On Windows, source installation requires the GNU toolchain (`x86_64-pc-windows-gnu`). This is
documented in the README and in the installation vignette.

## Downstream dependencies

There are no reverse dependencies on CRAN.
